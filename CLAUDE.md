Курсовая (тема: «Построение RAG-хранилища для LLM на PostgreSQL: чанкование,
эмбеддинги и контекстная выборка»), с прицелом на диплом и подачу на
Акселератор МИРЭА. Команда: Роман Антонников, Андрей Подольский
(бсбо 52-24). Научный руководитель: Игорь Котилевец.

Продукт: RAG-помощник для сайта МИРЭА — студенты задают вопросы вместо
обращения к кураторам/старостам. Курсовая — версия для первокурсников,
диплом — для всех курсов.

## Технические решения (согласованы с куратором)

**Чанкование.** Основная стратегия — structure-aware (режем по заголовкам
и абзацам, т.к. страницы МИРЭА уже структурно размечены). Recursive
character splitting — **дополняющий** (не запасной) вариант для
неструктурированных документов (сплошной текст, PDF-регламенты).

**Эмбеддинги.** Выбор команды (не решение куратора) — **Qwen3-Embedding-0.6B,
self-hosted**. Куратор отдельно не одобрял и не критиковал сам выбор модели;
в контексте разбора проблемы ретривала (ниже) он отметил, что у модели
такого размера ограниченный семантический охват на русском домене — это
один из двух факторов проблемы, а не оценка выбора модели как такового.

**Гибридный поиск — RRF**, не чистый вектор и не взвешенное среднее.
Не требует нормализации шкал. Подтверждена устойчивость к опечаткам на
мини-прототипе.

**Проблема ретривала — РЕШЕНО через Query Rewriting/Expansion.** Было:
3 из 15 вопросов проваливались не из-за отсутствия данных, а из-за
пайплайна — RRF не всегда ранжировал нужный чанк в топ при расхождении
терминологии («приёмная комиссия» vs «поступление»). Причина: маленький
эмбеддер слабо ловит семантику на русском + FTS не связывает однокоренные
слова без нормализации/синонимов.

Реализация (`_retrieve()` в `use_cases.py`): LLM генерирует 2 синонимичных
варианта запроса → **FTS идёт по всем 3 вариантам** (оригинал + 2
синонимичных) параллельно → **векторный поиск — только по оригиналу**
(не утраивается) → `rrf_fuse_multi()` фьюзит все 4 списка (3 FTS + 1
vector).

Асимметрия FTS×3 / vector×1 — осознанный выбор, не экономия по
недосмотру: FTS лексический (ищет точные леммы, синонимы ему критичны —
«приёмная комиссия» и «поступление» для него разные слова), а Qwen
семантический и уже проецирует близкие по смыслу фразы в близкие точки
пространства — три варианта запроса дали бы три почти одинаковых top-K
и почти не добавили бы RRF ничего нового. Симметричный вариант (vector
тоже по 3 запросам) возможен, дал бы небольшой прирост recall, но с
доп. задержкой (Qwen обрабатывает 3 текста вместо 1) — решили, что
не стоит того.

Результат: Context Recall вырос с 0.45 до 0.79, fallback упал с 27% до
0%.

**5 открытых мелких кейсов (score 3/5, БЕЗ fallback) — известны,
не переоткрывать на следующих сессиях:**
| # | Тема | Что не так | Причина |
|---|------|-----------|---------|
| Q1 | ЕГЭ ИВТ | LLM даёт только информатику=44, пропускает математику=39 и русский=40 | Конфликт в контексте — старый чанк со ссылкой «баллы на сайте» отвлекает LLM на самое очевидное число |
| Q2 | Общежитие первокурсника | Нет «иногородние имеют приоритет» | Данных в базе знаний нет |
| Q3 | Приёмная комиссия | «РТУ МИРЭА» вместо «МИРЭА» | Калибровка судьи, не реальная ошибка — это официальное название |
| Q13 | Иностранные граждане | Нет про нострификацию диплома | Context Recall=0.42 — данных в базе нет |
| Q15 | Условия общежития | Нет «2-3 человека в комнате», нет цен по типам | Данные в базе частичные |

Убывающая доходность: основной прирост (2.0→3.73) уже извлечён, дальше
улучшения точечные и не приоритетны прямо сейчас.

**Eval-метрики — ROUGE удалён полностью из кода** (`metrics.py`,
`pipeline.py`, `report.py`). Куратор прямо указал: ROUGE меряет
n-граммное совпадение формы текста, а не фактическую корректность, для
RAG это неверная метрика — было чистым legacy-полем, ни на что не
влиявшим. Перешли на **Ragas-стиль метрики** через `judge_ragas()`
(`llm_judge.py`), каждая — отдельный параллельный LLM-вызов:
Faithfulness, Answer Relevance, Context Recall.

**LLM-judge — смягчён.** Было: систематически уводил в fallback даже
при достаточном контексте (не единичные баги, а проблема порога
чувствительности). Исправлено в `prompt_templates.py`: маркер
«Недостаточно данных» теперь возвращается только если контекст вообще
не по теме, а не при любой неполноте — отсюда падение fallback с 27%
до 0%.

**Генерация ответа.** Промпт + LLM (сейчас GPT через OpenAI API), фолбек
на человека/техподдержку при неуверенном ответе.

**⚠️ ФЗ-152 — критичное юридическое требование.** Отправка данных ЛКС
(курс, факультет, долги по оплате — даже без ФИО) во внешний LLM API —
нарушение закона о персональных данных. **На проде обязательна локальная
LLM на серверах вуза** (например, Qwen/Llama). Текущий OpenAI API —
**строго временный инструмент прототипирования**, не решение для прода.
Явно документировать это разграничение в архитектуре — не смешивать
прод-путь с тестовым.

**Персонализация через личный кабинет.** Демо-концепция (не боевая
интеграция с реальным ЛКС МИРЭА — доступа к нему нет):
- Privacy-UX: **не** спрашивать согласие посреди диалога чекбоксами при
  каждом релевантном вопросе — это сбивает поток. Правильный паттерн:
  **один дисклеймер при первом входе в виджет ЛКС** («Бот видит данные
  вашего профиля для точных ответов. [Настроить приватность]»), детальные
  чекбоксы — в иконке настроек чата, не в основном диалоге
- Согласие — управляемое состояние в БД с таймстампом, отзываемое
- Без согласия бот отвечает как неавторизованному пользователю (общие
  ответы, при нехватке контекста просит уточнить в вопросе) — доступ
  **не блокируется**
- Для демо — 2–3 простых блока данных (например, «академический профиль»
  + «финансовый статус»), не сложная матрица всех полей
- Реализация: тестовая веб-версия с замоканными профилями и
  переключением в реальном времени (курс, пол и т.д.) — не ждём
  реального доступа к внутренней системе МИРЭА

**Масштаб базы знаний.** 97 чанков куратор считает малым объёмом для
презентации. Нужен либо явный аргумент/слайд про поддержание базы
актуальной (ручной HTML-сбор хрупкий, ломается при любом обновлении
страниц вуза), либо реальное увеличение объёма.

**Инфраструктура.** VPS + PostgreSQL + pgvector в Docker.

## Веб-версия (следующий блок, старт 21.09.2026)

**Один репозиторий.** Веб НЕ выносится в отдельный репозиторий — та же
кодовая база (`mirea-rag`), что и Telegram-бот. Причина: оба клиента
должны дёргать один и тот же RAG-backend (retrieval, RRF, Query
Expansion, Qwen-эмбеддер, LLM-judge) — дублирование этой логики в двух
репо создаёт риск рассинхронизации при будущих фиксах.

**Архитектура: тонкий API-слой поверх существующих use-cases.**
Существующая RAG-логика (`_retrieve()`, генерация ответа, eval) НЕ
переписывается и не дублируется. Поверх неё добавляется FastAPI-роут
(например, `POST /api/ask`), который вызывает те же use-cases, что уже
вызывает Telegram-бот. Telegram-бот и веб — два независимых клиента
одного backend, не две системы.

**Статус — демо/прототип для презентации**, не боевая интеграция:
- Реальная авторизация НЕ нужна — как обсуждали с куратором, доступа к
  настоящему ЛКС МИРЭА нет
- Два тестовых экрана:
  1. **Главная страница** — имитация сайта МИРЭА, внизу виджет
     поддержки, работает для всех неавторизованных, общие ответы
  2. **Страница ЛКС** — по заглушечной кнопке «Перейти в ЛКС» (без
     настоящего входа). Виджет заменяет живой колл-центр (5 дней в
     неделю, узкое окно) — работает в любое время
- Тестовые профили (курс, пол и т.д.) переключаются на странице в
  реальном времени, без бэкенда для профилей — просто фронтенд-стейт,
  который передаётся в API-запрос
- Privacy-механизм — см. раздел «Персонализация через личный кабинет»
  выше: один дисклеймер при входе, не чекбоксы посреди диалога

**Фронтенд — чистый HTML/CSS/JS, без фреймворка.** React/Vue и подобное
не нужны для демо такого масштаба — усложнение без пользы на этом
этапе.

**Как встроить в текущий репозиторий:**
- Backend: новый FastAPI-роут в существующем приложении (не новый
  сервис) — переиспользует уже работающие `use_cases.py`,
  `rrf.py`, `llm_judge.py` и т.д.
- Frontend: статические файлы (HTML/CSS/JS), отдаются тем же
  приложением (`StaticFiles` в FastAPI) или отдельной простой
  раздачей — НЕ отдельный деплой
- Telegram-бот продолжает работать как есть, никаких изменений в его
  логике не требуется

## Стек

- Бэкенд: Python, FastAPI
- БД: PostgreSQL + pgvector
- Эмбеддинги: Qwen3-Embedding-0.6B, self-hosted
- LLM: GPT через OpenAI API (**временно, только для прототипа** — см.

- Архитектурный ориентир (не обязателен к копированию, но полезен для

## Правила для Claude Code

- **При коммитах в Git: единственный автор — аккаунт Романа/аккаунт
  разработчика. Claude/Claude Code никогда не добавляется как соавтор
  коммита** (co-author trailer недопустим).
- Не менять зафиксированные архитектурные решения выше (chunking-стратегию,
  RRF, эмбеддинги, стек) без явного запроса в диалоге — это согласовано с
  научным руководителем, самовольные правки ломают согласованный план
  курсовой.
- ROUGE удалён из кодовой базы полностью — не возвращать его обратно
  ни в каком виде (ни как metric, ни как supplementary/legacy-поле).
- Не путать прод-путь LLM (локальная модель, обязательно из-за ФЗ-152) с
  текущим тестовым OpenAI API — не переносить временное решение в
  прод-конфигурацию по умолчанию.
- Privacy/согласие в ЛКС-версии — реализовывать как одноразовый
  дисклеймер при входе + настройки в отдельной иконке, а не как
  чекбоксы посреди диалога.
- При работе над веб-версией НЕ трогать существующую RAG-логику
  (`_retrieve()`, RRF, Query Expansion, eval-пайплайн) без явной
  необходимости — эта часть уже настроена и даёт 97% Judge≥4, случайная
  правка ради веб-интеграции рискует сломать то, что работает. Веб
  должен быть тонким слоем поверх, не рефакторингом backend.
