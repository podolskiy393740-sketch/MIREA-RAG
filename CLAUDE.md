# RAG-система МИРЭА — контекст проекта

Курсовая (тема: «Построение RAG-хранилища для LLM на PostgreSQL: чанкование,
эмбеддинги и контекстная выборка»), с прицелом на диплом и подачу на
Акселератор МИРЭА. Команда: Роман Антонников, Андрей Подольский
(бсбо 52-24). Научный руководитель: Игорь Котилевец.

Продукт: RAG-помощник для сайта МИРЭА — студенты задают вопросы вместо
обращения к кураторам/старостам. Курсовая — версия для первокурсников,
диплом — для всех курсов.

## Текущее состояние (на 20.09.2026)

Telegram-бот развёрнут и работает на VPS. База знаний: ~43 документа,
~108 чанков, все векторизованы (источники — Q&A-пары + HTML-страницы
сайта МИРЭА; 20.09 добавлены 11 таргетированных Q&A через delta-сидинг:
приёмная комиссия, ЕГЭ-баллы ИВТ, библиотека, кампусы, ОВЗ, льготы,
оплата, столовые, общежитие-условия, колледж).

Метрики на 15 тестовых вопросах (прогон 20.09.2026):
- Fallback: **0/15 (0%)** — было 4/15 (27%) на старте сессии
- Judge ≥ 4: **10/15 (67%)**
- Judge mean: **3.73/5**
- Faithfulness: **0.90** (LLM почти не галлюцинирует)
- Answer Relevance: **0.85**
- Context Recall: **0.79** (ретривал находит релевантные чанки в 79%)

Out-of-scope вопросы отбиваются в 100% случаев.

Известные кейсы score=3/5 (все без fallback, не требуют срочной правки):
- Q1 (ЕГЭ ИВТ): LLM выдаёт только информатика=44, пропускает математика=39
  и русский=40. F=0.60/CR=0.85 — данные в KB есть, вероятно конфликт со
  старым чанком «баллы опубликованы на сайте», который мешает LLM выводить
  все три числа.
- Q2 (Общежитие первокурсника): правильный процесс подачи, но нет фразы
  «иногородние имеют приоритет». Данных в KB может не быть. F=0.90/CR=0.75.
- Q3 (Приёмная комиссия): адрес и часы 100% верны. Судья снимает балл за
  «РТУ МИРЭА» вместо «МИРЭА» — проблема калибровки эталонного ответа,
  не реальная ошибка бота. F=0.70/CR=0.90.
- Q13 (Иностранные граждане): нет нострификации диплома. CR=0.42 — данных
  в KB нет, нужен отдельный Q&A-чанк. F=0.95/CR=0.42.
- Q15 (Условия общежития): типы комнат есть, нет «2-3 человека» и
  ценообразование по типу. F=1.00/CR=0.75. Куратор одобрил план
веб-версии («план годный»), дал технический фидбек 19.09.2026 — он
учтён и отражён ниже.

## Технические решения (согласованы с куратором)

**Чанкование.** Основная стратегия — structure-aware (режем по заголовкам
и абзацам, т.к. страницы МИРЭА уже структурно размечены). Recursive
character splitting — **дополняющий** (не запасной) вариант для
неструктурированных документов (сплошной текст, PDF-регламенты).

**Эмбеддинги.** Выбор команды (не решение куратора) — **Qwen3-Embedding-0.6B,
self-hosted**. Куратор отдельно не одобрял и не критиковал сам выбор модели;
в контексте разбора проблемы ретривала (ниже) он отметил, что у модели
такого размера ограниченный семантический охват на русском домене — это
один из двух факторов проблемы, а не оценка выбора модели как такового.

**Гибридный поиск — RRF**, не чистый вектор и не взвешенное среднее.
Не требует нормализации шкал. Подтверждена устойчивость к опечаткам на
мини-прототипе.

**Проблема ретривала — частично решена (20.09.2026).** Исходно 3–4/15
вопросов проваливались из-за расхождения терминологии («приёмная
комиссия» vs «поступление») — маленький эмбеддер слабо ловит семантику,
FTS не связывает однокоренные слова без нормализации. **Реализован
Query Expansion** (`_expand_queries()` в `use_cases.py`): LLM генерирует
2 синонимичных варианта запроса перед поиском, ищем по всем трём.
Дополнительно добавлены таргетированные Q&A-чанки для проблемных тем.
Итог: 0/15 fallback, CR=0.79. **Опциональный следующий шаг** (для
диплома): Cross-Encoder Reranker — отдельная модель точнее переранжирует
топ-N кандидатов после retrieval. Это дополнительный слой после RRF,
не замена гибридному поиску.

**Eval-метрики — Ragas-стиль, ROUGE удалён.** Куратор прямо указал:
ROUGE меряет n-граммное совпадение формы текста, а не фактическую
корректность, для RAG это неверная метрика. ROUGE полностью удалён из
кодовой базы (metrics.py, pipeline.py, report.py). Активные метрики:
Faithfulness (не выдумала ли LLM факты вне контекста), Answer Relevance
(отвечает ли на вопрос), Context Recall (нашёлся ли релевантный чанк).

**LLM-judge порог — откалиброван (решено).** Куратор указал на
системную проблему: судья уводил в fallback даже при достаточном
контексте. Порог `has_answer()` перенастроен; после сессии 20.09
fallback-rate = 0/15. Eval-метрики реализованы в Ragas-стиле через
LLM-вызовы: Faithfulness, Answer Relevance, Context Recall (не ROUGE).

**Генерация ответа.** Промпт + LLM (сейчас GPT через OpenAI API), фолбек
на человека/техподдержку при неуверенном ответе.

**⚠️ ФЗ-152 — критичное юридическое требование.** Отправка данных ЛКС
(курс, факультет, долги по оплате — даже без ФИО) во внешний LLM API —
нарушение закона о персональных данных. **На проде обязательна локальная
LLM на серверах вуза** (например, Qwen/Llama). Текущий OpenAI API —
**строго временный инструмент прототипирования**, не решение для прода.
Явно документировать это разграничение в архитектуре — не смешивать
прод-путь с тестовым.

**Персонализация через личный кабинет.** Демо-концепция (не боевая
интеграция с реальным ЛКС МИРЭА — доступа к нему нет):
- Privacy-UX: **не** спрашивать согласие посреди диалога чекбоксами при
  каждом релевантном вопросе — это сбивает поток. Правильный паттерн:
  **один дисклеймер при первом входе в виджет ЛКС** («Бот видит данные
  вашего профиля для точных ответов. [Настроить приватность]»), детальные
  чекбоксы — в иконке настроек чата, не в основном диалоге
- Согласие — управляемое состояние в БД с таймстампом, отзываемое
- Без согласия бот отвечает как неавторизованному пользователю (общие
  ответы, при нехватке контекста просит уточнить в вопросе) — доступ
  **не блокируется**
- Для демо — 2–3 простых блока данных (например, «академический профиль»
  + «финансовый статус»), не сложная матрица всех полей
- Реализация: тестовая веб-версия с замоканными профилями и
  переключением в реальном времени (курс, пол и т.д.) — не ждём
  реального доступа к внутренней системе МИРЭА

**Масштаб базы знаний.** 97 чанков куратор счёл малым объёмом для
презентации; после delta-сидинга 20.09 — ~108 чанков. Ручной HTML-сбор
хрупкий (ломается при обновлении страниц вуза) — нужен либо аргумент
про поддержание актуальности на слайде, либо дальнейшее увеличение
объёма (парсинг дополнительных разделов сайта).

**Инфраструктура.** VPS + PostgreSQL + pgvector в Docker.

**Интерфейс.** Сейчас — Telegram-бот для тестов и метрик. Далее — веб:
(1) главная страница как имитация сайта МИРЭА с виджетом поддержки для
неавторизованных, (2) страница ЛКС с персонализацией по профилю.

## Стек

- Бэкенд: Python, FastAPI
- БД: PostgreSQL + pgvector
- Эмбеддинги: Qwen3-Embedding-0.6B, self-hosted
- LLM: GPT через OpenAI API (**временно, только для прототипа** — см.
  требование по ФЗ-152 выше)
- Архитектурный ориентир (не обязателен к копированию, но полезен для
  структуры слоёв): чистая архитектура из chernenko-s/mirea-rag (автор —
  Слава, не Тимофей) — domain/application/infrastructure/presentation

## Правила для Claude Code

- **При коммитах в Git: единственный автор — аккаунт Романа/аккаунт
  разработчика. Claude/Claude Code никогда не добавляется как соавтор
  коммита** (co-author trailer недопустим).
- Не менять зафиксированные архитектурные решения выше (chunking-стратегию,
  RRF, эмбеддинги, стек) без явного запроса в диалоге — это согласовано с
  научным руководителем, самовольные правки ломают согласованный план
  курсовой.
- ROUGE для eval — не использовать, даже если уже где-то реализовано;
  переходить на Ragas/TruLens.
- Не путать прод-путь LLM (локальная модель, обязательно из-за ФЗ-152) с
  текущим тестовым OpenAI API — не переносить временное решение в
  прод-конфигурацию по умолчанию.
- Privacy/согласие в ЛКС-версии — реализовывать как одноразовый
  дисклеймер при входе + настройки в отдельной иконке, а не как
  чекбоксы посреди диалога.
